# Panoptis — оркестратор анализа документов закупок

## Как это работает

```
downloader.py (скрапер)               orchestrator (этот пакет)
─────────────────────────             ──────────────────────────
качает файлы в                        watcher.py следит за DOCS_DIR
docs/<reg_number>/...                 через watchdog
                                             │
пишет docs/<reg_number>/_done.flag ──────────┤ on_created(_done.flag)
(JSON: список файлов + doc_type)            │
                                             ▼
                                       db.enqueue_purchase(reg_number)
                                       → INSERT INTO purchases (status='pending')
                                             │
                                             ▼
                              main.py (воркер, отдельный процесс)
                              каждые POLL_INTERVAL_SEC секунд:
                                 - берёт одну закупку 'pending'
                                 - ставит 'processing'
                                 - для каждого файла в папке закупки:
                                     text_extractor.extract_text()
                                     → llm_client.analyze_document()
                                       (один самостоятельный запрос
                                        на /completion, БЕЗ истории
                                        диалога — это же обходит
                                        стороной баг сбоя модели на
                                        втором сообщении в чате)
                                     → db.insert_item(...) / insert_log(...)
                                 - ставит 'done'
```

Watcher и воркер — два независимых процесса. Такое разделение позволяет:
- рестартовать воркер (например, при изменении промпта) без потери
  событий watcher'а — они уже лежат в SQLite как `pending`;
- пережить падение оркестратора целиком — при следующем запуске
  `watcher.scan_existing_flags()` подхватит всё, что было пропущено.

## Почему очередь в SQLite, а не in-memory

GPU один, обработка строго последовательная — очередь не про
конкурентность, а про надёжность: если воркер упал посреди закупки,
после перезапуска он просто продолжит с `pending`, ничего не потеряется.
Дополнительная инфраструктура (Redis/Celery) для одного локального
воркера избыточна.

## Запуск (Windows/PowerShell)

```powershell
# 1. Убедись, что llama.cpp сервер уже запущен (см. настройки в "Промпты")
#    Обнови -n на 1024 (или больше) и -c на 8192, если ещё не сделал:
& "C:\agent\core\llama.cpp\build\bin\Release\llama-server.exe" `
    -m "C:\agent\core\llama.cpp\models\Aura_7B.Q8_0.gguf" `
    --host 127.0.0.1 --port 8080 `
    -c 8192 -ngl 99 --threads 4 --batch-size 512 `
    -n 1024 --temp 0.1 --top-p 0.9 --repeat-penalty 1.1

# 2. Установи зависимости оркестратора
pip install -r requirements.txt

# 3. В отдельном окне — watcher
python watcher.py

# 4. В отдельном окне — воркер
python main.py
```

Перед первым запуском поправь пути в `config.py` под свою структуру
папок (`DOCS_DIR` должен совпадать с `config.DOCS_DIR` скрапера).

## Схема БД

См. `db.py` — три таблицы: `purchases` (очередь/статус закупки),
`purchase_items` (сырые находки LLM с привязкой к файлу-источнику
и его типу — это тот самый "словарь", который потом можно использовать
для дообучения классификатора или анализа, в каких типах документов
объект закупки реально встречается), `processing_log` (журнал по
каждому файлу — успех/ошибка, для отладки).

Дедупликация позиций между документами одной закупки (если один товар
упомянут и в ТЗ, и в проекте контракта) намеренно НЕ делается на этом
этапе — это отдельный шаг поверх `purchase_items`, когда накопится
достаточно данных, чтобы понять реальные паттерны расхождений
в формулировках (тогда в дело идёт `rapidfuzz`, как и планировалось).

## Что нужно проверить/донастроить перед первым реальным запуском

1. **grammar.gbnf** — GBNF синтаксис у llama.cpp местами капризный.
   Проверь грамматику отдельным тестовым запросом к `/completion`
   до интеграции в пайплайн — если сервер откажется её принимать,
   сверься с примерами в `llama.cpp/grammars/*.gbnf`.
2. **MAX_DOC_CHARS в config.py** — грубая оценка на глаз, для реальных
   документов возможно потребует калибровки под реальное соотношение
   символы/токены для русского текста.
3. **SUPPORTED_EXTENSIONS** — сейчас только `.docx`/`.xlsx`. Если
   в закупках часто встречаются `.pdf` — это следующий шаг (потребует
   pdfplumber или OCR для сканов).
4. Пути в `config.py` — сейчас захардкожены под `C:\agent\data\...`,
   поправь под свою структуру.
